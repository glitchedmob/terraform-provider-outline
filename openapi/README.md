# Outline API generation

## Pinned sources

`outline.openapi.json` is the unmodified `spec3.json` from [outline/openapi at `40f51b75efad84e3e860af3e1c8b5a58fd74bb48`](https://github.com/outline/openapi/tree/40f51b75efad84e3e860af3e1c8b5a58fd74bb48). The upstream commit is dated 2026-09-23. The file's SHA-256 is `71c211078aff5b950df1b478aed628a242df26fe94c3b5f055fef9b1d46f2731`. `LICENSE` is the original BSD-3-Clause license from that commit. This specification and code generated from it retain that license; provider code and the local overlay use the repository's MPL-2.0 license. Release archives include the upstream notice as `OUTLINE-OPENAPI-LICENSE`.

The IAM contracts target [Outline v1.10.1, commit `4a5a616a21be800257dc11cef4263d0dd0412156`](https://github.com/outline/outline/tree/4a5a616a21be800257dc11cef4263d0dd0412156) only. Compatibility with other releases is not claimed. Do not verify collection changes against `main`; its description and archive/delete APIs have changed since this release.

`oapi-codegen.yaml` selects 29 IAM operations:

- `auth.info`
- Users list, info, invite, update, update_role, suspend, activate, delete
- Groups list, info, create, update, delete, memberships, add_user, remove_user, update_user
- Collections list, info, create, update, delete, memberships, add_user, remove_user, group_memberships, add_group, remove_group

The original full specification is committed, but we generate only these operations and their model dependencies. The final IAM scope has six resources, `outline_user`, `outline_group`, `outline_group_member`, `outline_collection`, `outline_collection_group`, and `outline_collection_user`, plus three data sources, `outline_user`, `outline_group`, and `outline_collection`. Collection group grants use the generated group_memberships, add_group, and remove_group operations. Direct user grants use memberships, add_user, and remove_user. `usersUpdate` supports display-name changes using an explicit target UUID. Documents and document grants are not managed. API key creation/deletion require application sessions and are not generated or managed. Passwords, OIDC handshakes, IdP login, token exchange, and magic-link authentication are outside this provider.

## Generation and drift checks

Run from the repository root:

```shell
make generate
make check-generated
```

`make generate` uses `go tool oapi-codegen` v2.8.0, pinned in `go.mod`, to apply `outline.overlay.yaml` with strict target matching and generate models and client methods in `internal/client/client.gen.go`. Nullable fields use `github.com/oapi-codegen/nullable` v1.2.0; the client runtime is v1.7.0. Generation reads only committed local specifications and overlay files. It never downloads a live specification. Go may download pinned tool dependencies on the first run.

Commit source, overlay, config, and generated output together. `make check-generated` regenerates and rejects tracked changes and untracked files under `internal/client/`. The Generated Client workflow runs this on pull requests and pushes to `main`. Unit tests also compare generation into a temporary file byte-for-byte and verify the upstream source checksum. When deliberately updating upstream, update the pin, checksum test, license, and this document after rechecking the server contracts.

## Calling conventions for resource authors

`internal/provider/apiClient` embeds `*client.ClientWithResponses` and uses the origin-restricted bearer transport, provider user agent, per-attempt timeout, redirect rejection, and bounded rate-limit HTTPDoer wrapper. Provider Configure only builds this client; it does not call `auth.info` or any other endpoint.

Import `github.com/glitchedmob/terraform-provider-outline/internal/client`. Each RPC is a POST:

```go
response, err := api.UsersInfoWithResponse(ctx, client.UsersInfoJSONRequestBody{Id: userID})
```

`userID` is `github.com/google/uuid.UUID`, also aliased as `github.com/oapi-codegen/runtime/types.UUID`. Most ID fields use that type. GroupUser's returned id is a composite string, not a UUID. Required body fields are values; optional fields are pointers. Use the generated `...JSONRequestBody` type for calls, not a parallel handwritten request struct. Auth info has no body: `api.AuthInfoWithResponse(ctx)`.

Response wrappers expose `StatusCode()`, `HTTPResponse`, raw `Body`, `JSON200`, and documented `JSON400`/`JSON401`/`JSON403`/`JSON404`/`JSON429` variants. HTTP errors do not automatically become Go errors. Check status, the selected JSON variant, and required nested data before using it. Optional response fields stay pointers so missing data is detectable; decoding does not validate required fields or enum values. Use `.Valid()` on enums when validating input. Unknown statuses/content types retain raw Body. Read `Retry-After` from HTTPResponse on 429 responses. Generated wrappers do not retry requests or produce Terraform diagnostics. The resource and data source helpers add response validation and diagnostics; reuse those checks rather than handling only transport errors.

Key models are `User`, `Invite`, `Group`, `GroupUser`, `Collection`, `Membership`, `GroupMembership`, `PaginationResponse`, and `Auth`. Use `PermissionRead`, `PermissionReadWrite`, `PermissionAdmin` for collection grants; `GroupPermissionMember`/`GroupPermissionAdmin` for group membership; `UserRoleAdmin`/`UserRoleMember`/`UserRoleViewer`/`UserRoleGuest` for users. Collection defaults and direct grants are separate permissions.

Nullable fields have three states. A zero `nullable.Nullable[T]` omits the field, `nullable.NewNullNullable[T]()` writes JSON null, and `nullable.NewNullableWithValue(value)` writes a value. In particular, `CollectionsUpdateJSONRequestBody.Permission` must send null to make a collection private; omitting it preserves the current default and can trigger an unintended caller-admin grant in v1.10.1. The collection resource always sends the intended permission value or JSON null on create and update. Direct user/group grants use non-null `*Permission`.

List bodies use `*int` Limit/Offset. Responses return PaginationResponse with total and nextPath. The release middleware produces nextPath even for the last page. Advance offset using the returned page metadata and stop against total; do not rely on nextPath becoming empty or follow it through a different HTTP client. `checkResponse` and `checkEnvelope` validate status and success envelopes, redact the configured key from API diagnostics, and never retry writes. `nextOffset` rejects malformed and non-progressing pagination. The bearer transport waits on a context-aware five-requests-per-second limiter.

`walkGroups` rejects duplicate IDs and changing totals. It uses the release's default `updatedAt` ordering; concurrent changes can produce a diagnostic requiring a new lookup rather than an incomplete result. Group string validators count UTF-16 code units to match the release's Zod validators, including supplementary Unicode characters. The group data source checks all pages for exact, case-sensitive name matches and rejects ambiguous results. Group list memberships are only a preview. Use paginated `GroupsMembershipsWithResponse` for the full membership set. Admin `includeListOnly` can expose otherwise inaccessible collections but does not grant access to their contents.

In v1.10.1, omitting `users.list.filter` excludes suspended users, even for admins. Explicit `filter = all` includes pending, active, and suspended users for admins. `walkUsers` explicitly requests `filter = all`, orders by `createdAt ASC`, validates each returned user, and rejects duplicate IDs and changing totals. User email lookups compare exact lowercase, normalized emails across the complete list and reject ambiguity. Do not substitute an active-only list when checking email conflicts or proving absence.

Do not send X-Client-Version, which can change pagination totals, or X-Api-Version, which switches collection descriptions to rich-text presentation. The provider's default calls preserve the release's markdown description presentation.

Only those four exact POST URLs can retry. The wrapper requires the four-field JSON error envelope without unknown or duplicate fields, JSON content type, a single positive Retry-After, a positive RateLimit-Limit, RateLimit-Remaining of zero, and a positive RateLimit-Reset consistent with Retry-After. Integer seconds and future HTTP dates are supported. Missing, zero, negative, fractional, overflowing, duplicate, stale, or inconsistent metadata never causes a replay. Neither do non-429 statuses, transport errors, response read/close errors, non-rebuildable bodies, or malformed error bodies. Generic proxy errors do not meet this contract. A proxy or plugin that fabricates the exact Outline contract cannot be distinguished at the HTTP layer; this contract assumes the configured instance preserves the released endpoint semantics.

`rate_limit_wait_seconds` is a total quota-wait budget per API call, default 120 seconds, configurable from 0 through 3600. Zero disables retries. Delays must fit the remaining budget and are never shortened to squeeze in an early retry. Waits are at least one second and account for timer overshoot. Each API call permits at most three retries independently of the wait budget, bounding network attempts as well as quota waits. Repeated limits cannot busy-loop or stall indefinitely. Each request body is rebuilt only after a verified rejection, and the rejected response body is closed before sleeping. All retry counters and budgets are per call; clients retain per-instance origin, key, pacing, and configuration. There is no broad quota cache or cross-process coordination. The context can cancel both waits and attempts. The separate default 30-second network timeout includes pacing and response reads, not quota waits.

### Group member resource contracts

The group membership contract is verified against `server/routes/api/groups/schema.ts`, `server/routes/api/groups/groups.ts`, `server/policies/group.ts`, `server/policies/utils.ts`, and `server/presenters/groupUser.ts`, and `server/presenters/user.ts` in the pinned v1.10.1 tree. Do not substitute behavior from `main` or infer ownership protection from another resource.

`outline_group_member` manages one group/user pair, not a group's entire membership set. Required `group_id` and `user_id` are canonical lowercase, nonzero UUIDs with `RequiresReplace`. Its computed stable Terraform ID and import format are `group_id/user_id`, with exactly one slash. The server presenter ID is `userId-groupId`; validate the returned pair but do not use that presenter ID as Terraform identity. The optional computed `permission` defaults to `member` and accepts only `member` or `admin`. An imported admin membership with omitted permission reconciles to `member`, rather than leaving the permission unmanaged.

Reuse `requireIAMAdmin` from the user helper for every operation, including reads and import refresh. This requires an active workspace admin. Resolve parents through the existing `readGroup` and `readUser` helpers, and use `managedGroup` to refuse externally linked or synchronized groups before membership reads or mutations. Do not copy the user resource's API-key-owner mutation restriction. Self-membership is supported because the release treats a workspace admin as a group admin regardless of their stored group permission. Membership operations do not change workspace roles. The pinned policies and handlers impose no last-group-admin or group-owner protection, and the resource does not add one.

Read and preflight through every page of `GroupsMembershipsWithResponse`. Group list memberships are previews, not a complete set. Validate page metadata, stable totals, duplicate pairs, and every returned item's group/user IDs, including consistency with its nested user and presenter ID. Group endpoints call `presentUser` without `includeDetails`, so both inline and listed users omit email even for admins. `validateGroupMemberUser` validates these public users separately; do not weaken `validateUser` or the parent account-read contract. Complete the walk even after finding the target pair, so later malformed pages cannot be ignored. Only a complete validated list can prove that pair absent. Missing parents must be established through `readGroup` or `readUser` and their release-verified checks. A membership endpoint's `403` or `404` is always an error, never evidence of absence; retain state on failed checks.

Create completes the parent checks and full membership preflight, rejects an existing pair with an import diagnostic, then calls `GroupsAddUserWithResponse` with explicit intended permission. The release's add handler is an upsert. A concurrent writer can insert the same pair between preflight and write, and the provider can overwrite that writer's permission. There is no atomic create-only API to close this race. Coordinate writers for a pair and document the limitation rather than claiming Create can prevent every adoption race.

Permission updates use `GroupsUpdateUserWithResponse` with explicit intended permission. Delete uses `GroupsRemoveUserWithResponse` for only the target pair. Validate mutation responses before replacing trusted state; never retry writes automatically. After successful create preflight, retain the trusted compound pair ID before attempting the write, not only after receiving a success response. Transport errors, failed envelopes, and malformed responses can follow a committed write and must preserve that recovery state. Terraform taints failed creates; users must inspect the actual membership, fix the error, and untaint an existing pair to reconcile it in place, or import it if state was lost. A retained pair ID alone does not prove that the write committed.

### Collection resource and lookup contracts

The collection contract is verified against `server/routes/api/collections/schema.ts`, `server/routes/api/collections/collections.ts`, `server/models/Collection.ts`, `server/models/Document.ts`, `server/policies/collection.ts`, and `server/presenters/collection.ts` in the pinned v1.10.1 tree. Deletion side effects also use `server/queues/processors/CollectionsProcessor.ts`, `server/queues/tasks/DetachDraftsFromCollectionTask.ts`, and `server/queues/tasks/CleanupDeletedDocumentsTask.ts`. The collection-grant migrations and `UserMembership`/`GroupMembership` models confirm that soft deletion retains direct and group collection-grant rows. Do not substitute later archive/delete or description behavior from `main`.

`outline_collection` manages an active collection by stable canonical lowercase, nonzero UUID. Short URL IDs, names, and full URLs are not import IDs. Name changes update in place. Names contain 1 to 100 Unicode code points, no URL, and no surrounding whitespace. The Collection ORM counts code points, unlike the group Zod limits. Duplicate collection names are valid, so Create does not adopt or deduplicate by name.

The resource manages only name, Markdown description, default permission, and sharing. Description defaults to an empty string and allows at most 100000 Unicode code points. The provider does not send `X-Api-Version`, preserving Markdown presentation; rich-editor edits can change the returned Markdown. Omitted or null permission means private, not unmanaged. Valid configured defaults are `read` and `read_write`; the resource rejects the server's `admin` default and archived collections during read, import, update, and delete. The lookup can read both. Sharing defaults to false, explicitly overriding the server's true creation default. Workspace sharing policies still apply. `allow_destroy` is a local false-by-default guard, not a server field, and import resets it to false. Match description, permission, and sharing before applying an imported resource or configuration defaults will change them.

`readCollection` reuses `requireIAMAdmin` for every UUID read, including refresh and import. Unlike users and groups, `collections.info` uses `rejectOnEmpty` before authorization. Only the decoded Outline `404 not_found` envelope with status 404 and `ok = false` proves absence. A 403 never proves absence, even after a complete admin workspace list. A foreign workspace's existing collection can return 403 and cannot appear in that list. Unexpected route/proxy 404 responses and malformed success bodies retain errors and state. Do not add the user/group enumeration fallback to this helper.

`walkCollections` verifies an active admin and requests `includeListOnly = true` with explicit `statusFilter = []`. In v1.10.1, an omitted status filter excludes archives, but the empty array includes active and archived collections. Admin `includeListOnly` includes private workspace collections without granting private-document access. Trash and other workspaces are excluded. Validate all pages, duplicate UUIDs, and stable totals. Name lookup requires an exact, case-sensitive match, rejects ambiguity across active and archived names, then reads the matching UUID and verifies the name has not changed. The data source returns null for private permission and an empty string for a null description; it does not summarize direct/group grants.

Creation unavoidably gives the caller direct collection-admin membership through the server's `AfterCreate` hook. The provider retains a usable returned UUID before validating the rest of the response. Create uses the generated raw request and generated response parser while retaining a valid JSON response body for identity-only recovery. A malformed setting that prevents full generated decoding does not discard a canonical returned UUID; no separate API response structs are used. Terraform taints failed creates; inspect the workspace, fix the error, and untaint an existing collection to reconcile in place, or import it if state was lost. A response without a usable UUID requires manual inspection before retrying because duplicate names are allowed.

Updates always supply the desired permission value or JSON null. The release handler compares permission to `read_write` before checking whether it was supplied. Omission can therefore create a caller-admin membership while preserving the stored default. Explicit values avoid this omission bug, but a real change from `read_write` to another default still creates that membership if the caller has no direct membership. An existing direct membership is not upgraded. These are server side effects, not provider-managed grants. Setting a private default does not remove existing direct or group access.

Deletion is blocked unless `allow_destroy = true` has been applied and stored before destruction. `collections.delete` soft-deletes the collection and trashes published, non-archived, non-template, non-trial documents through the default Document scope. Archived documents, templates, and trial-import documents remain. Drafts detach asynchronously. Direct and group collection-grant rows remain, and the workspace default-collection setting is cleared if it referenced the collection. Deleted documents become eligible for permanent cleanup after 30 days. Soft deletion is destructive, not a safe handoff or an immediate full purge, and the provider has no restore operation. The server refuses deletion of the last non-trashed workspace collection. A failed delete response, including 403 or 404, retains state; only a later verified info read can establish absence.

Collection grant resources must reuse `readCollection` and `requireIAMAdmin`, but verify their own grant-endpoint absence and authorization contracts. An empty workspace list, a grant-endpoint 403/404, or admin metadata access does not prove absence or document access. Collection defaults and explicit grants have separate lifecycle rules.

### Collection group resource contracts

The collection group-grant contract is verified against `server/routes/api/collections/schema.ts`, `server/routes/api/collections/collections.ts`, `server/policies/collection.ts`, `server/policies/group.ts`, `server/models/GroupMembership.ts`, and `server/presenters/groupMembership.ts` in the pinned v1.10.1 tree. The missing-grant error also uses `server/errors.ts` and `server/onerror.ts`. Do not infer grant behavior from group membership endpoints or a later server release.

`outline_collection_group` manages one explicit collection/group grant, not the collection's entire grant set or effective user access. Required `collection_id` and `group_id` are canonical lowercase, nonzero UUIDs with `RequiresReplace`. Its computed stable Terraform ID and import format are `collection_id/group_id`, with exactly one slash. The server's `GroupMembership.id` is a grant-row UUID, not Terraform identity. Required `permission` accepts only `read`, `read_write`, or `admin`, with no default. Import discovers the stored permission through a full grant read; configuration must supply that required value to retain it on the next apply.

Reuse `requireIAMAdmin` for every operation, including reads and import refresh. The caller must be an active workspace admin. Resolve parents through the existing release-verified `readCollection` and `readGroup` helpers. Refuse archived collections before grant reads or mutations, but do not reuse `managedCollection` wholesale: its rejection of an `admin` default is specific to the collection resource's default-access management. This grant resource does not edit the default and supports collections with an `admin` default. Do not use `managedGroup` to reject externally linked or synchronized groups. The release's add/remove grant handlers authorize collection `update` and group `read`, not group `update`, and never modify group names or users. The group read policy allows same-workspace, non-guest readers without a synchronization restriction.

The generated add/upsert body is `{id: collection_id, groupId: group_id, permission: intended_permission}`; removal sends only `{id: collection_id, groupId: group_id}`. The server defaults an omitted add permission to `read_write`, so never omit it. List requests send `{id: collection_id, limit: 100, offset: current_offset}`.

Read and preflight through every page of `CollectionsGroupMembershipsWithResponse`, without query or permission filters. Grants are in `data.groupMemberships`, not `data.collectionGroupMemberships`, and are `GroupMembership`, not `GroupUser`. Validate success envelopes, page metadata, stable totals, duplicate grant IDs and pairs, collection/group IDs, permissions, and explicit collection-grant scope. Require a canonical nonzero grant-row UUID and explicit null `documentId` and `sourceId`; document and inherited grants are not this resource's target. Require the success envelope's `status = 200` and `ok = true`. Validate `data.groups` consistently with the grants. Complete the walk even after finding the target; a malformed later page cannot be ignored. Only a complete validated list can prove the pair absent.

Missing parents must be established through `readGroup` or `readCollection` and their existing checks. The group helper requires verified admin identity and complete workspace enumeration for its missing-ID fallback. The collection helper accepts only the decoded Outline `404 not_found` envelope. A collection 403 never proves absence, even after a complete workspace list. Grant-endpoint 403/404 responses are errors, never evidence of absence. Failed authorization, parent verification, archive checks, or response validation retain state.

Create completes parent checks and the full grant preflight, rejects an existing pair with an import diagnostic, then calls `CollectionsAddGroupWithResponse` with explicit intended permission. Permission changes use the same endpoint, also with explicit permission. The released handler is an upsert: a writer can insert the same pair after preflight, and the provider can overwrite that writer's permission. There is no atomic create-only API to prevent this race. Coordinate writers for each pair rather than claiming preflight closes it. Manage each pair in only one resource and Terraform state.

After successful create preflight, retain the trusted compound pair ID in state before attempting the mutation. Transport errors, failed envelopes, or malformed responses can follow a committed write and must preserve that recovery state. Validate mutation responses before replacing trusted state and never retry writes automatically. Terraform taints failed creates; inspect the actual grant, fix the error, and untaint an existing pair to reconcile in place, or import it if state was lost. A retained pair ID alone does not prove the write committed.

Delete calls `CollectionsRemoveGroupWithResponse` for only the configured pair. If parents or the pair are already absent, only the verified parent reads or complete grant list establish that absence. A raced remove returns HTTP 400 with the Outline envelope `ok = false`, integer `status = 400`, `error = "invalid_request"`, and exact message `This Group is not a part of the collection`. Accept this specific response as an absent pair only after a fresh complete validated group-grant list confirms absence. Any other 400, any 403/404 from the grant endpoint, a still-present pair, or a failed/incomplete confirmation read is an error and retains state. Do not swallow ambiguous errors or equate the server's validation failures with absence.

Reusable provider helpers are `activeCollectionGrantTarget` for archive refusal without rejecting an admin default, `checkCollectionGrantEnvelope` for strict grant success envelopes, and the existing `readCollection`, `readGroup`, and `requireIAMAdmin`. `validateCollectionGroup`, `readCollectionGroupPages`, and `observeCollectionGroup` implement the group-specific grant validation and complete observation. The direct user-grant resource uses its independently verified presenter and missing-pair contract below, not these group-specific rules.

The released `GroupMembership` hooks can refuse downgrading or deleting the last stored collection-admin grant across direct user and group grants. Workspace-admin metadata access and default collection permission do not replace that stored grant. Report these server errors and retain state. Removing this pair does not remove either parent, content, direct user grants, document grants, other group grants, or default workspace access.

### Collection user resource contracts

The direct collection-grant contract is verified against the pinned v1.10.1 sources below. It uses `Membership` backed by `UserMembership`, not `GroupMembership` or `GroupUser`. No new API operations or generated models are needed for this resource.

`outline_collection_user` manages one explicit direct collection/user pair, not the collection's grant set, effective access, or workspace roles. Required `collection_id` and `user_id` are canonical lowercase, nonzero UUIDs with `RequiresReplace`. The computed stable Terraform ID and import format are `collection_id/user_id`, with exactly one slash. The server's `Membership.id` is a grant-row UUID, not Terraform identity. Required `permission` accepts only `read`, `read_write`, or `admin`, with no default. Import reads the stored permission without changing it; configuration must supply it explicitly before the next apply.

Reuse `requireIAMAdmin` for every operation, including read and import. Before observing or mutating the pair, refuse the API-key owner's own user UUID during create, read, import, update, and delete. This is a provider safety rule to prevent dropping or demoting the caller's stored collection control, not a server prohibition. Use another active admin's key to manage that pair. A creator's automatic grant is unavoidable and must never be silently adopted. Manage it only intentionally with a different active admin key and import.

Resolve parents through the existing `readCollection` and `readUser` helpers. Use the active-collection grant check to refuse archives without rejecting the server's `admin` default permission. The default is not this resource's setting. The released add/remove handlers authorize actor collection `update` and target user `read`; the latter only checks same-workspace identity. Pending, suspended, guest, and viewer targets are supported without a provider role/suspension restriction. A grant does not activate a suspended account, and suspended accounts cannot authenticate.

Role-dependent actions remain separate from the stored grant. Guests need membership even where collection default access exists. The collection policies accept explicit `read_write` or `admin` membership for document writes by viewers and guests, subject to document-specific policy. Collection sharing is refused for guests. Viewer/guest collection download policy depends on the team's `ViewersCanExport` preference, but `collections.export` separately authenticates at least workspace `member`; that preference and a collection-admin grant do not bypass the endpoint's role requirement. An `admin` collection grant does not promote workspace role. A direct `read` grant does not cap access from defaults or a `read_write` group grant, and workspace-admin metadata access does not grant private-document access.

The generated add/upsert body is `{id: collection_id, userId: user_id, permission: intended_permission}`; removal sends only `{id: collection_id, userId: user_id}`. Never omit add permission. The server otherwise selects the target's role default, `read` for a viewer and `read_write` for every other role. List requests send `{id: collection_id, limit: 100, offset: current_offset}` without query or permission filters.

Read and preflight through every page of `CollectionsMembershipsWithResponse`, using `data.memberships` and `data.users`. Do not substitute group lists, default permission, or calculated effective access. Validate `status = 200` and `ok = true`, pagination metadata, stable totals, duplicate grant-row IDs and collection/user pairs, canonical nonzero grant-row UUID strings and valid decoded parent/target UUIDs, permission and public user-role enums, matching users, and explicit collection-grant scope. Require explicit null `documentId` and `sourceId`; missing fields, document grants, and inherited rows are not acceptable direct collection grants. List and add users are public presentations without email; do not weaken the separate parent-account validation that requires detailed admin reads. Complete the walk even after finding the target. Only a full validated list can prove the pair absent.

Missing parents must be established only through `readUser` or `readCollection` and their release-verified checks. The user helper requires active-admin verification and the complete `filter = all` user list, including suspended accounts, for its missing-ID fallback. The collection helper accepts only the decoded Outline `404 not_found` envelope. A collection 403 never proves absence. Membership-list failures, including 400/403/404, self-target refusal, failed parent or archive checks, and malformed pages return diagnostics and retain state.

Create completes parent checks and the full membership preflight, rejects an existing pair with an import diagnostic, then calls `CollectionsAddUserWithResponse` with explicit intended permission. Permission updates use that same endpoint. The released upsert is not an atomic create-only operation: a writer can insert the pair after preflight, and the provider can overwrite that writer's permission. Coordinate writers and manage each pair in only one resource and Terraform state. Preflight cannot prevent this race.

After successful create preflight, retain the trusted compound pair ID before attempting the write. Transport errors, failed envelopes, and malformed responses can follow a committed write and must preserve recovery state. Validate mutation responses before replacing trusted state and never retry ambiguous writes. Only `collections.add_user` can retry the verified pre-mutation 429 contract described above; removal cannot retry. Terraform taints failed creates; inspect the actual grant, fix the error, and untaint an existing pair to reconcile in place, or import it if state was lost. A retained pair ID alone does not prove that the write committed. Replacement can interrupt access by removing the direct grant first.

Delete calls `CollectionsRemoveUserWithResponse` only for the configured direct pair. Verified parent reads or a complete direct-membership list can establish that it is already absent. The sole accepted raced-remove error is HTTP 400 with the Outline envelope `ok = false`, integer `status = 400`, `error = "invalid_request"`, and exact message `User is not a collection member`, followed by a fresh complete validated direct-membership list confirming absence. Any other 400, any grant-endpoint 403/404, a still-present pair, or failed/incomplete confirmation remains an error and retains state. A malformed response cannot establish absence.

Report the release's last-manager downgrade/removal errors and retain state. Default permission and workspace-admin metadata access do not replace the stored admin grant. Removing this pair does not remove or suspend the user, remove the collection or content, or change group memberships, group/document grants, other direct grants, or collection defaults.

## IAM behavior and limits

Use an unrestricted admin-owned Outline API key for these IAM operations. User, group member, collection, and both collection-grant resources verify that the caller is an active admin. All user modifying actions reject the key owner's UUID or normalized email before a write; group member operations support the key owner's membership. Direct collection user grants refuse the key owner's own pair during every operation, including read and import. Endpoint-scoped keys and server policies can still reject calls. OIDC provisioning uses invitations with `suppressEmail` and separate SSO configuration, not passwords or magic-link sign-in.

The release inviter ignores existing accounts, reports them in `unsent`, and returns only new users. Create checks the full admin user list first and still rejects `unsent` to handle races. Existing users are never adopted or modified during Create; import their UUID instead. Guest invitations become member invitations in v1.10.1, so the resource reads the stored role and reconciles it. The supported API roles `admin`, `member`, `viewer`, and `guest` are tested on this release. Editions and licenses may restrict roles; the provider reports server errors or a response that fails to confirm the intended role.

The user resource requires an explicit final `suspended` boolean. Against the freshly read account, a role change on a currently suspended user with planned `suspended = true` is refused before any modifying request unless `allow_temporary_activation_for_role_change` is explicitly known true. The option defaults to false, including on import. Opting in activates the account, changes its role and configured name, then suspends it again. These endpoints use separate transactions, and existing sessions can regain access during that interval. Best-effort suspension after failure cannot undo access or guarantee recovery after process death or failed cleanup. An unchanged role or name-only update never activates a retired account. Explicit `suspended = false` intentionally reactivates it without requiring the option. Activation is not a sign-in or proof that an IdP account can authenticate.

User creation retains a newly returned matching UUID in state before follow-up validation, reads, and writes. Terraform taints failed creates. After fixing the error, untaint to reconcile in place; if state was lost, inspect the workspace and import the account's UUID. Default destruction only suspends the account, retains its memberships and content, and removes Terraform state. Recreating the same email refuses the retained account and requires import. Opt-in `delete_permanently` calls `users.delete`, which is irreversible through this provider. The released server anonymizes and soft-deletes users; this does not guarantee a full purge or delete their documents.

User email is required and immutable. Invitations use lowercase, normalized email while state preserves equivalent configured casing. Configuration changes require replacement, not renaming; Outline's confirmation flow must run outside the provider. The optional computed name has no default. Omission uses `Pending user` on creation and leaves the name unmanaged afterward. The released User ORM validates name length by Unicode code points, unlike group Zod limits, and rejects names containing its `NotContainsUrl` pattern. Configured names are reapplied if IdP sign-in changes them. Role defaults to member, `suppress_email` defaults to true and is creation-only, and `delete_permanently` defaults to false. See the [OIDC guide](../docs/guides/oidc.md) for replacement, import, and recovery procedures.

Group description requires an update after creation in this release; the group resource performs that follow-up update. It persists the returned ID before the second write. A failed create still taints the resource in Terraform; untaint after fixing the error to recover with an in-place update. Group update cannot clear externalId with null, and externally synchronized groups reject manual name/membership changes. The resource rejects externally synchronized groups and exposes no external_id argument. The data source can read an externally synchronized group by UUID. The group member resource also refuses these groups, including during reads and import. The collection group resource supports them because its operations grant collection access without changing group names or members. Collection creation defaults `templateManagement` to admin at the server. The collection resource leaves that setting, sort, commenting, color, icon, and document content outside its schema. It explicitly manages sharing and default permission as described above.

The group resource implements UUID import, in-place updates, refresh, and deletion for manually maintained groups. The v1.10.1 `groups.info` handler authorizes a nil model, producing `403 authorization_error` for nonexistent IDs. `readGroup` does not equate 403 or an unexpected route/proxy 404 with absence. It requires `auth.info` to confirm an admin and `walkGroups` to complete an unfiltered workspace list with consistent pagination totals. A listed ID, failed check, or malformed page preserves the error and state. Its data source requires exactly one configured UUID or name and returns description and mention settings.

The missing-user contract was independently verified against v1.10.1. `users.info` also authorizes a nil model and returns `403 authorization_error` for a nonexistent UUID. `readUser` only treats this response as absence after verifying an active admin and completing the full `filter = all` workspace user list, including suspended accounts. A bare 403 is never absence. An unexpected `users.info` 404 also requires the complete list check, since a missing route or proxy response does not prove the account was deleted. A listed UUID or failed verification preserves the error and resource state. The user data source requires exactly one UUID or email and returns the current name, role, and suspension state. Future resources must verify their own missing-object contracts rather than copy either fallback blindly. The group member resource reuses these parent helpers but never treats membership endpoint errors as absence. The collection group resource keeps the collection absence contract separate from grant-endpoint behavior, as described above. The direct collection user-grant resource reuses these parent helpers but independently validates the direct-membership and exact raced-removal contracts above.
